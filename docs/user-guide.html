What it is

A local web app that records browser journeys and plays them back.

You give it a URL. It opens a real browser, and everything you do in that window — clicking, typing, ticking boxes, picking from dropdowns — arrives in the studio as a list of steps. The steps are plain and editable: an action, a selector, a value. Nothing is hidden in a binary recording.

Afterwards you can replay the journey whenever you want, watch it pass or fail step by step with screenshots, and export the whole thing as an NUnit, Playwright Test, or pytest file that runs in a normal test project.

Start here

On first launch the studio seeds one worked example, Demo signup — happy path, pointed at a practice form it serves itself at /demo-form.html. Open it and press Run before recording anything of your own — it takes about three seconds and proves the whole chain works on your machine.

The home screen

A junction, not a dashboard. Every part of the studio is one click from here.

Record creates a scenario and opens the browser in one move — the same as New & record on the scenarios page. Import takes a scenario json somebody exported. The rest are destinations: the same five entries as the sidebar, which stays available on every screen.

Which browser

Edge on its own is enough. So is Chrome. Nothing has to be downloaded.

Playwright normally ships its own browser builds, but it can also drive a browser you already have. In Settings → Browser, the two “(installed)” options — Microsoft Edge and Google Chrome — launch what is on the machine already. Recording, replay, assertions, screenshots and traces all work this way with an empty Playwright cache.

SettingWhat it launchesDownload?
chromiumPlaywright's own Chromium buildYes, ~150 MB
msedgeThe Edge installed on this machineNo
chromeThe Chrome installed on this machineNo
firefoxPlaywright's own Firefox buildYes
webkitPlaywright's own WebKit build (Safari's engine)Yes

Both Chromium and Edge are ready on this machine right now. Edge is the better default if you want tests running against the browser your users actually have.

Two catches

Don't press Install msedge in Settings — that runs Edge's own installer, which you don't need. The Check button is the useful one: it starts the browser and reports the version back.

Record video of the run is the one feature with an outside dependency. Playwright records WebM, and the studio transcodes that to mp4 — but the ffmpeg Playwright bundles is a stripped build with no mp4 muxer at all. Switch video on and Settings offers Download ffmpeg, which fetches a static build into the studio's own tools folder; nothing is installed machine-wide. Until one is there the video stays .webm and the run log says why.

01Record a journey

Press record, drive the form like a person, stop. That's the whole loop.

Hit New & record on the scenarios page, or Record more steps inside a scenario you already have. A real browser window opens at your start URL with a small toolbar pinned to the bottom-right corner.

What the toolbar does

  • REC — a pulsing dot while capture is live.
  • ⏸ — pause. Click around, log in, dismiss a cookie banner; none of it is recorded. Press again to resume.
  • ✔ Assert — opens the checks menu. Covered in step 3.
  • ✎ — type a note that lands in the step list as a comment, so future-you knows why a step is there.

What gets captured

  • Clicks, double-clicks and right-clicks — on the meaningful element, so clicking the label inside a button records the button.
  • Typing, collapsed into one Fill per field rather than one step per keystroke.
  • Checkboxes and radios as Check / Uncheck, dropdowns as Select with the option label in the description.
  • Enter and Esc as Press steps — the ones that usually submit or dismiss something.
  • Navigation, but only when it wasn't caused by the click you just made. A click that loads a page is one step, not two.

Fast-forwarding a form

Re-typing the first eight fields by hand every time you want to record the ninth gets old. While the window is open, the ⏩ on any step replays the saved steps into that same window, up to and including that one — or Play all here on the recorder bar for the lot. The form fills itself, the window is handed back to you, and recording carries on from where the playback stopped.

Capture is paused while it plays, so the studio does not record its own playback as a second set of steps.

When you're done, Stop & keep writes the captured steps into the scenario. Closing the browser window does exactly the same thing — nothing is lost either way, and a Discard button is there if the take was no good.

Passwords

A password field is never written into a step. The recorder lifts the value into a scenario variable and the step reads {{password}} instead. The variable itself is masked in the UI — but it is stored in plain text in the scenario's json file, so blank it out before you commit or share that file.

02Read the steps

A recording is a starting point, not a finished test. This is where you make it yours.

Every step shows its action, a plain-language label the recorder wrote from the field's own label, the selector it settled on, and the value. Untick a step to skip it without deleting it; drag it up or down with the arrows; press ▶ on any row to replay from that row while you're debugging the tail of a journey.

Opening a step with the pencil gives you the full picture — including every other selector the recorder considered for that element.

Under Advanced

  • Timeout — override the default for one slow step instead of slowing every step down.
  • Wait before — a blunt pause, for when an animation has to finish.
  • Carry on if this fails — for the step that dismisses a banner that isn't always there.
  • Screenshot after this step — capture just the moment that matters, without turning on screenshots for everything.
While recording

With the recorder still live, the crosshair button on a step highlights that selector's element in the real browser window and tells you how many things it matched. “1 match” is what you want; “4 matches” means the step will act on the first one.

03Add checks

A journey that clicks through without asserting anything only proves nothing crashed.

Press ✔ Assert on the browser toolbar — or Add check in the studio — and pick what kind of check you want. The page goes into PICK mode: a bar appears at the top, and whatever you hover is outlined with its selector shown on a tag.

CheckPasses when
AssertVisibleThe element is on screen and visible.
AssertHiddenThe element is gone or hidden — a spinner that finished, an error that cleared.
AssertTextThe element's text matches. Prefilled with what was on screen when you picked it.
AssertValueAn input holds a particular value.
AssertCheckedA checkbox or radio is in the state you expect.
AssertUrlThe address bar matches — a redirect landed where it should.
AssertTitleThe page title matches.
AssertCountA selector matches exactly N elements — five rows in a table, no validation errors.

How text is matched

The expected value in a text, value, url or title check reads three ways:

You writeIt means
Welcome backContains, ignoring case. The default, and usually what you want.
=Welcome backExact match, after trimming whitespace.
/order-\d+/Regular expression.

Checks retry until the step's timeout, so a value that arrives half a second late still passes. You don't need to sprinkle waits around them.

04Run it

Press Run. Watch each step go green, or find out exactly which one didn't.

Results appear against the steps as the run moves through them. Run uses whatever Headless is set to and works in its own throwaway browser.

Watch uses a window you can see. A bar appears at the top of the page showing which step is running, with its own Stop button, and the window is left open at whatever point the run reached — so you can stop part-way and carry on by hand from there.

Running in your own browser

By default the studio drives a private browser of its own. Switch on Use the browser I am already in under Settings → Browser and runs instead open a tab in your browser: your logins, your cookies, your extensions. Stop the run and the tab is still sitting there for you to carry on in.

There is one catch. A browser started the normal way cannot be driven — Chromium refuses remote debugging against your everyday profile. Open a debuggable browser starts one with its own profile folder and the debugging port switched on; use that window for the studio and for whatever you are testing, and the two share it. Check connection tells you whether the studio can see it.

Video and trace are skipped in this mode: both are fixed when a browser context is created, and that context is yours, not the studio's.

Add some slow motion in the right-hand rail when you want to follow along.

Turning a run into a user manual

User manual on a run report drafts a manual and opens it for editing — it does not hand you a PDF straight away. Manuals are their own thing, listed under Manuals in the sidebar, and they keep their own copy of every picture, so clearing your run history never guts a document you have written.

In the editor you can rewrite any instruction, reorder steps, add or delete them, switch a step out of the document without losing it, edit the title and introduction, and replace any picture with your own — a cropped shot, an annotated one, a photo. Press Preview to see the finished document, and Download PDF when it reads right.

Every step has a notes button — on saved steps and on steps as they are being recorded, which is when you still remember why the step exists. Write what a reader should be told to do, in markdown; there is a live preview beside the box, and a switch to leave plumbing steps out of the manual entirely.

The draft comes out as numbered steps: your instructions, and under each one the screenshot that step actually produced. Waits and scrolls are dropped, skipped steps are dropped, and a step you never wrote anything for falls back to a plain description — "Choose "za" in "Country"." — so the document is never blank where you forgot.

Turn on Screenshot every step in Settings before the run, or the manual will tell you how many steps came out without a picture.

Addresses come out as links, not as walls of query string — a reader gets "Click the sign-in link below. It takes you to login.microsoftonline.com to sign in." with a clickable link beneath, while the full address lives in the link itself and still works when clicked in the PDF.

Capturing pages for site duplication

The small camera on a scenario card turns on page capture. Switching it on asks where the files should go — it suggests a folder beside the app, with quick picks for your data folder or Documents, and warns you if the path sits under bin where a rebuild would wipe it. Each scenario remembers its own folder. With capture on, a run saves every distinct page the journey reaches — a full-page screenshot and the html behind it: 

…\Videos\..\Captures\acme-site-walk\
├── 01-localhost-home.png / .html
├── 02-localhost-about.png / .html
├── 03-localhost-contact.png / .html
└── pages.md                     what was captured, and from which url

One capture per url, so a journey that does five things on one page still saves it once. The screenshot is full-page rather than viewport-sized, and the html is the live DOM after scripts have run — between them, enough to rebuild a page later. Studio:CaptureFolder in appsettings.json changes the default the prompt suggests.

When a step fails

The run stops there, the remaining steps are marked skipped, and the failure explains itself in terms of what was actually on the page: 

Text is "Welcome Jane. You are on the pro plan, and we will
mail jane+9546@example.com.", expected to contain "enterprise plan"

A screenshot of the failing moment is captured automatically. If you'd rather step through it, turn on Record trace.zip, re-run, and open the trace from the report — it gives you a frame-by-frame timeline with the DOM at every step: 

playwright show-trace trace.zip

05Export it

When a journey earns its place in the real suite, take it with you.

  • C# / NUnit — a PageTest fixture for a project referencing Microsoft.Playwright.NUnit.
  • TypeScript — a spec for @playwright/test.
  • Python — a pytest test needing pytest-playwright.
  • Scenario json — the studio's own format. Import it on another machine to get the scenario back, steps and alternatives intact.

Variables survive the trip as real constants, and the built-ins become the target language's equivalent rather than a literal {{random:4}} left in your source: 

private const string Plan = "pro";

await Page.Locator("#email").First.FillAsync(
    "jane+" + Random.Shared.Next(0, 10000).ToString("0000") + "@example.com");
await Page.Locator("input[name=\"plan\"][value=\"" + Plan + "\"]").First.CheckAsync();
await Expect(Page.Locator("#successDetail").First).ToContainTextAsync(Plan + " plan");

How selectors are chosen

This is the part that decides whether a test still passes next month.

For every element you touch, the recorder builds a list of candidates, throws away any that don't match exactly one element on the page, and takes the best survivor. The rest are kept on the step so you can swap to them later.

  1. [data-testid="submit-signup"]

    Test ids win, always — they exist precisely so tests can hold onto them. Also reads data-test, data-qa, data-cy and data-automation-id.

  2. #email

    An id, but only one that doesn't look machine-generated. Ids full of hex, long digit runs, a random-looking tail, or a framework prefix — :r, mat-, mud — get demoted below role=, because they change on every render. MudBlazor's #mudinput08267ls7 is the classic trap: it looks like a perfectly good id and is gone by the time you replay.

  3. input[name="plan"][value="pro"]

    Form attributes. Radios and checkboxes share a name, so the value is what tells them apart. Then [aria-label] and [placeholder].

  4. role=button[name="Create account"]

    Role and accessible name — what a screen reader would call it. Survives restyling and markup churn, and breaks loudly if the label changes, which is usually correct.

  5. #signup > fieldset > label:nth-of-type(2) > input

    A css path, and only because nothing better existed. If you see one of these, it's a hint that the element could use a test id.

Worth doing

Add data-testid to the handful of controls your tests depend on. The recorder will pick them up first, and those steps stop caring about your markup entirely.

Variables

For the bits that shouldn't be the same every run.

Write {{name}} in any step value — or inside a selector — and define the name in the scenario's Variables panel. The editor warns you about any name that isn't defined. These built-ins need no definition and are resolved fresh on every run:

PlaceholderBecomes
{{guid}}A fresh guid
{{randomemail}}test+418203@example.com
{{random:6}}Six random digits, zero-padded
{{randomtext:8}}Eight random letters
{{now}}2026-09-13 10:40:57
{{now:HH\:mm}}A custom format — escape the colon
{{today}}2026-09-13
{{timestamp}}Unix milliseconds

A signup form that rejects duplicate addresses is the obvious case: put jane+{{random:4}}@example.com in the email step and the scenario stops failing on its second run.

Where things live

Scenarios, runs, screenshots, traces and settings all sit in one folder, deliberately outside the project's bin so that rebuilding the app never deletes your tests: 

%LOCALAPPDATA%\PlaywrightStudio
├── settings.json
├── tools\ffmpeg\ffmpeg.exe      downloaded on demand, for mp4
├── scenarios\<id>.json          one file per scenario
└── runs\<timestamp>\
    ├── run.json                 results, timings, errors
    ├── step-003-ok.png          screenshots
    └── trace.zip                when tracing was on

Videos are the exception — they land in a Videos folder beside the app itself, named after the scenario and run so you can pick one out in Explorer: 

…\bin\Debug\net10.0\Videos\demo-signup-happy-path-20260913-184155.mp4

That folder sits under bin, so a rebuild clears it. Point Studio:VideoFolder in appsettings.json somewhere permanent if you want to keep them.

A scenario file is readable json, so it's fine to commit next to the app it tests — putting the folder inside a repo is a reasonable way to share scenarios with a team.

Moving the folder

Settings → Where things are stored has a Browse button that opens a folder picker. Pick somewhere new and the studio asks before doing anything, offering to copy your scenarios, runs and manuals across first — that option is on by default, because changing the folder without it would leave your work behind in the old one.

The copy leaves the originals exactly where they were, so a wrong turn costs disk space rather than anything you have recorded. The downloaded ffmpeg is not copied; it re-downloads on demand. The new folder takes effect when the studio next starts, and the page says so rather than leaving you wondering why nothing moved.

Note

Studio:DataRoot in appsettings.json still works and still wins. When it is set, the folder cannot be changed in the app and the field says why — clear the setting to take control back in the UI.

Surviving replay

The page you replay against is never quite the page you recorded. These are the gaps the studio closes on its own.

What differsWhat the run does
The saved selector stopped matching — an id was regenerated, a label was reworded Falls back to the other selectors the recorder kept for that element, and tells you which one worked so you can promote it.
The first match is a hidden duplicate — a collapsed mobile nav, an offscreen slide Acts on the first visible match. Hidden-element steps (AssertHidden, AssertCount, Upload) opt out.
The journey opens a tab Follows the new tab and carries on there, and steps back if it closes.
A confirm or alert box appears Accepts it — you clicked OK while recording — and notes it in the run log. Playwright dismisses these by default, which would take the other branch.
A dropdown's option values are environment ids Tries the value, then the visible label.
A cookie banner now covers the control Cannot click through it — nothing can — but names the element doing the covering instead of just timing out.

None of this rescues a step that is simply wrong, and none of it is a substitute for a data-testid on the controls that matter. It buys you runs that fail for real reasons rather than incidental ones.

When it misbehaves

The recorder captured nothing

Check the toolbar in the browser window. If it reads PAUSED, capture is off — press the pause button again. If there's no toolbar at all, the page never loaded; the status line under the record button in the studio says what went wrong.

A step passes alone but fails in sequence

Almost always timing — the previous step's page hasn't settled. Add a WaitForSelector for whatever should be on screen first, rather than a fixed WaitForTimeout, which is slower and still flaky.

“4 elements matched, 1 of them visible”

The step worked, but the selector is loose. Actions go to the first visible match rather than the first in the markup — a site's header is often duplicated for mobile and desktop, and the hidden copy usually comes first, so acting on it would just wait forever for something that can never be clicked. Still worth tightening: open the step, try the other selectors on offer, and use the crosshair to get down to one match.

A step times out

The message says which of the three things went wrong, so read past the timeout:

  • Nothing on the page matches that selector — the page changed, or the previous step didn't land where you expected.
  • None are visible — the element exists but is hidden behind a collapsed menu, a tab you haven't opened, or a modal that isn't up yet. Add a click or a WaitForSelector before it.
  • No iframe matched — the step was recorded inside a frame that didn't appear this time, typically a pop-up that only shows on a first visit. Delete the step, or tick Carry on if this fails under Advanced.

A recorded click does nothing on replay

Usually a custom widget that reacts to mousedown or a keystroke rather than a plain click. Swap the step to Focus followed by Press, or to Hover then Click if it's a menu that opens on hover.

Known edges

  • A cross-origin iframe can't see the <iframe> tag holding it, so the recorder names such a frame by its own name or url instead — iframe[name="edr_l_first"]. A frame with neither falls back to a bare iframe, and on a page with several the run takes the first one.
  • Canvas and custom-drawn widgets have nothing to select — add a check by hand against something near them.
  • One recording at a time. The studio owns a single browser.
